지금까지 Tailwind로 기사, 문서, 또는 블로그 포스트를 스타일링하는 것은 타이포그래피에 대한 예리한 눈과 복잡한 사용자 정의 CSS가 많이 필요한 지루한 작업이었습니다.

기본적으로 Tailwind는 단락, 제목, 목록 등에서 모든 기본 브라우저 스타일링을 제거합니다. 이는 애플리케이션 UI를 구축할 때 정말 유용합니다. 사용자 에이전트 스타일을 되돌리는 데 시간을 덜 쓰기 때문입니다. 하지만 CMS의 리치 텍스트 에디터나 마크다운 파일에서 나온 콘텐츠를 스타일링하려고 할 때는 놀랍고 직관적이지 않을 수 있습니다.

실제로 많은 불만을 받고 있으며, 사람들이 정기적으로 다음과 같은 질문을 합니다:

> 왜 Tailwind가 내 `h1` 요소의 기본 스타일을 제거하나요? 이것을 어떻게 비활성화하나요? 다른 모든 기본 스타일도 잃는다는 것은 무슨 뜻인가요?
> 여러분의 말씀을 들었지만, 단순히 기본 스타일을 비활성화하는 것이 정말 원하는 것이라고 확신하지 못합니다. 대시보드 UI의 일부에서 `p` 요소를 사용할 때마다 성가신 여백을 제거하고 싶지 않을 것입니다. 그리고 블로그 포스트가 사용자 에이전트 스타일을 사용하기를 원하지 않을 것입니다 — 여러분은 그것들이 끔찍하지 않고 _멋지게_ 보이기를 원할 것입니다.

`@tailwindcss/typography` 플러그인은 기본 스타일을 비활성화하는 것과 같은 어리석은 일의 단점 없이 여러분이 _정말로_ 원하는 것을 제공하려는 우리의 시도입니다.

이 플러그인은 바닐라 HTML 콘텐츠의 모든 블록에 적용할 수 있는 새로운 `prose` 클래스를 추가하여 아름답고 잘 포맷된 문서로 변환합니다:

```javascript
const SimplePropertyRetriever = {
  getOwnEnumerables(obj) {
    return this._getPropertyNames(obj, true, false, this._enumerable);
    // 또는 for...in을 Object.hasOwn으로 필터링하여 사용할 수 있습니다.
  },
  getOwnNonenumerables(obj) {
    return this._getPropertyNames(obj, true, false, this._notEnumerable);
  },
  getOwnEnumerablesAndNonenumerables(obj) {
    return this._getPropertyNames(
      obj,
      true,
      false,
      this._enumerableAndNotEnumerable
    );
    //  또는 단순히 Object.getOwnPropertyNames(obj)를 사용할 수 있습니다.
  },
  getPrototypeEnumerables(obj) {
    return this._getPropertyNames(obj, false, true, this._enumerable);
  },
  getPrototypeNonenumerables(obj) {
    return this._getPropertyNames(obj, false, true, this._notEnumerable);
  },
  getPrototypeEnumerablesAndNonenumerables(obj) {
    return this._getPropertyNames(
      obj,
      false,
      true,
      this._enumerableAndNotEnumerable
    );
  },
  getOwnAndPrototypeEnumerables(obj) {
    return this._getPropertyNames(obj, true, true, this._enumerable);
    // 또는 필터링되지 않은 for...in을 사용할 수 있습니다.
  },
  getOwnAndPrototypeNonenumerables(obj) {
    return this._getPropertyNames(obj, true, true, this._notEnumerable);
  },
  getOwnAndPrototypeEnumerablesAndNonenumerables(obj) {
    return this._getPropertyNames(
      obj,
      true,
      true,
      this._enumerableAndNotEnumerable
    );
  },
  // 내부 정적 속성 검사 콜백
  _enumerable(obj, prop) {
    return Object.prototype.propertyIsEnumerable.call(obj, prop);
  },
  _notEnumerable(obj, prop) {
    return !Object.prototype.propertyIsEnumerable.call(obj, prop);
  },
  _enumerableAndNotEnumerable(obj, prop) {
    return true;
  },
  // http://stackoverflow.com/a/8024294/271577 에서 영감을 받음
  _getPropertyNames(obj, iterateSelf, iteratePrototype, shouldInclude) {
    const props = [];
    do {
      if (iterateSelf) {
        Object.getOwnPropertyNames(obj).forEach((prop) => {
          if (props.indexOf(prop) === -1 && shouldInclude(obj, prop)) {
            props.push(prop);
          }
        });
      }
      if (!iteratePrototype) {
        break;
      }
      iterateSelf = true;
      obj = Object.getPrototypeOf(obj);
    } while (obj);
    return props;
  },
};
```

플러그인 사용 방법과 포함된 기능에 대한 자세한 정보는 [문서를 읽어보세요](https://github.com/tailwindcss/typography/blob/master/README.md).

## 앞으로 무엇을 기대할 수 있는가

앞으로 이어지는 것은 제가 플러그인 자체를 테스트하기 위해 작성한 절대적인 헛소리입니다. **굵은 텍스트**, 순서 없는 목록, 순서 있는 목록, 코드 블록, 인용문, *그리고 심지어 기울임꼴*과 같은 생각할 수 있는 모든 합리적인 타이포그래피 요소를 포함합니다.

이러한 모든 사용 사례를 다루는 것이 중요한 이유는 몇 가지가 있습니다:

1.  모든 것이 기본적으로 좋게 보이기를 원합니다.
2.  정말로 첫 번째 이유뿐입니다. 그것이 플러그인의 전체 요점입니다.
3.  세 개 항목이 있는 목록이 두 개 항목이 있는 목록보다 더 현실적으로 보이기 때문에 여기에 세 번째 가짜 이유가 있습니다.

이제 다른 헤더 스타일을 시도해보겠습니다.

### 타이포그래피는 쉬워야 합니다

그래서 여러분을 위한 헤더입니다 — 우리가 일을 제대로 했다면 운이 좋다면 그것이 꽤 합리적으로 보일 것입니다.

타이포그래피에 대해 현명한 사람이 한 번 말한 것은:

> 여러분의 물건이 쓰레기처럼 보이지 않기를 원한다면 타이포그래피는 꽤 중요합니다. 좋게 만드세요. 그러면 나쁘지 않을 것입니다.

## 제목을 겹치면 어떻게 될까요?

### 그것도 좋게 보이는지 확인해야 합니다.

때때로 제목이 서로 바로 아래에 있을 수 있습니다. 그런 경우에는 두 번째 제목의 위쪽 여백을 되돌려야 하는 경우가 많습니다. 제목이 단락 뒤에 오는 것보다 제목들이 서로 더 가깝게 있는 것이 보통 더 좋아 보이기 때문입니다.

### 제목이 단락 뒤에 올 때...

제목이 단락 뒤에 올 때, 위에서 언급한 것처럼 조금 더 많은 공간이 필요합니다. 이제 더 복잡한 목록이 어떻게 보이는지 살펴보겠습니다.

- **저는 종종 목록 항목에 제목이 있는 이런 일을 합니다.**

  어떤 이유로 이것이 멋지게 보인다고 생각하는데, 이는 스타일을 올바르게 만드는 것이 꽤 성가시기 때문에 불행합니다.

  저는 종종 이러한 목록 항목에 두 개 또는 세 개의 단락을 가지고 있기도 하므로, 어려운 부분은 단락들 사이, 목록 항목 제목, 그리고 별도의 목록 항목들 사이의 간격을 모두 의미 있게 만드는 것입니다. 정말 어렵습니다. 여러분이 이런 방식으로 글을 쓰지 말아야 한다고 강하게 주장할 수 있습니다.

- **이것이 목록이므로 최소한 두 개의 항목이 필요합니다.**

  저는 이미 이전 목록 항목에서 제가 무엇을 하고 있는지 설명했지만, 목록이 하나의 항목만 가지고 있다면 목록이 아니며, 우리는 정말로 이것이 현실적으로 보이기를 원합니다. 그래서 제가 실제로 스타일을 작성할 때 볼 수 있는 무언가를 가지도록 이 두 번째 목록 항목을 추가한 것입니다.

- **세 번째 항목을 추가하는 것도 나쁜 아이디어가 아닙니다.**

  저는 두 개의 항목만 사용하는 것이 괜찮았을 것이라고 생각하지만, 세 개는 확실히 더 나쁘지 않으며, 제가 임의의 것들을 타이핑하는 데 문제가 없는 것 같으므로 포함시키는 것이 좋겠습니다.

이런 종류의 목록 후에 저는 보통 마무리 문장이나 단락을 가집니다. 제목으로 바로 넘어가는 것이 이상하게 보이기 때문입니다.

## 코드는 기본적으로 괜찮게 보여야 합니다.

저는 대부분의 사람들이 코드 블록을 스타일링하고 싶다면 [highlight.js](https://highlightjs.org/) 또는 [Prism](https://prismjs.com/) 같은 것을 사용할 것이라고 생각하지만, 구문 강조가 없어도 기본적으로 _괜찮게_ 보이도록 만드는 것이 나쁘지 않습니다.

작성 시점의 기본 `tailwind.config.js` 파일이 어떻게 보이는지 여기 있습니다:

```js
module.exports = {
  purge: [],
  theme: {
    extend: {},
  },
  variants: {},
  plugins: [],
};
```

희망적으로 그것이 여러분에게 충분히 좋게 보일 것입니다.

### 중첩된 목록은 어떨까요?

중첩된 목록은 기본적으로 항상 나쁘게 보이기 때문에 Medium과 같은 편집자들은 심지어 그것을 허용하지 않습니다. 하지만 여러분 중 일부 바보들이 그것을 할 것이기 때문에 우리는 최소한 작동하도록 만드는 부담을 져야 합니다.

1.  **중첩된 목록은 거의 좋은 아이디어가 아닙니다.**
    - 여러분이 정말로 "체계적"이거나 뭔가를 느낄 수 있지만, 여러분은 단지 화면에 읽기 어려운 역겨운 모양을 만들고 있을 뿐입니다.
    - UI에서 중첩된 네비게이션도 나쁜 아이디어입니다. 가능한 한 평평하게 유지하세요.
    - 소스 코드에 폴더를 많이 중첩하는 것도 도움이 되지 않습니다.
2.  **더 많은 항목이 필요하므로, 여기에 또 다른 것이 있습니다.**
    - 두 단계보다 깊게 스타일링할지 확신하지 못합니다.
    - 두 개는 이미 너무 많고, 세 개는 확실히 나쁜 아이디어입니다.
    - 네 단계 깊이로 중첩한다면 여러분은 감옥에 속합니다.
3.  **두 개의 항목은 정말 목록이 아니고, 세 개는 좋습니다.**
    - 다시 한 번, 사람들이 실제로 여러분의 콘텐츠를 읽기를 원한다면 목록을 중첩하지 마세요.
    - 아무도 이것을 보고 싶어하지 않습니다.
    - 우리가 이것을 스타일링해야 한다는 사실에 화가 납니다.

Markdown에서 목록에 대한 가장 성가신 것은 `<li>` 요소가 목록 항목에 여러 단락이 없는 한 자식 `<p>` 태그가 주어지지 않는다는 것입니다. 이것은 제가 그 성가신 상황도 스타일링해야 한다는 것을 의미합니다.

- **예를 들어, 여기에 또 다른 중첩된 목록이 있습니다.**

  하지만 이번에는 두 번째 단락과 함께입니다.

  - 이 목록 항목들은 `<p>` 태그를 가지지 않을 것입니다
  - 각각 한 줄뿐이기 때문입니다

- **하지만 이 두 번째 최상위 목록 항목에서는 그럴 것입니다.**

  이것은 특히 이 단락의 간격 때문에 성가십니다.

  - 여기서 볼 수 있듯이, 제가 두 번째 줄을 추가했기 때문에 이 목록 항목은 이제 `<p>` 태그를 가집니다.

    이것이 제가 말하는 두 번째 줄입니다.

  - 마지막으로 여기에 또 다른 목록 항목이 있어서 더 목록 같습니다.

- 중첩된 목록이 없는 마무리 목록 항목입니다. 왜 안 되겠습니까?

그리고 마지막으로 이 섹션을 마무리하는 문장입니다.

### 때때로 저는 제목에서도 `code`를 사용합니다

아마도 나쁜 아이디어일 수 있지만, 역사적으로 저는 그것을 좋게 보이게 만드는 데 어려움을 겪었습니다. 하지만 이 _"코드 블록을 백틱으로 감싸기"_ 트릭은 정말 잘 작동합니다.

제가 과거에 했던 또 다른 일은 링크 안에 `code` 태그를 넣는 것입니다. 예를 들어 [`tailwindcss/docs`](https://github.com/tailwindcss/docs) 저장소에 대해 말하고 싶다면. 백틱 아래에 밑줄이 있다는 것을 좋아하지 않지만, 그것을 피하는 데 필요한 광기만큼은 절대 가치가 없습니다.

#### 우리는 아직 `h4`를 사용하지 않았습니다

하지만 이제 사용했습니다. 여러분의 콘텐츠에서 `h5` 또는 `h6`을 사용하지 마세요. Medium이 두 개의 제목 수준만 지원하는 데는 이유가 있습니다, 여러분 동물들. 솔직히 `h5` 또는 `h6`을 사용한다면 여러분에게 소리치기 위해 `before` 가상 요소를 사용하는 것을 고려했습니다.

기본적으로 그것들을 전혀 스타일링하지 않습니다. `h4` 요소는 이미 너무 작아서 본문 텍스트와 같은 크기이기 때문입니다. `h5`로 무엇을 해야 할까요, 본문 텍스트보다 _더 작게_ 만들까요? 아니요, 감사합니다.

### 하지만 여전히 겹친 제목에 대해 생각해야 합니다.

#### `h4` 요소로도 그것을 망치지 않는지 확인해보겠습니다.

휴, 운이 좋다면 우리는 이 텍스트 위의 제목들을 스타일링했고 그것들이 꽤 좋게 보일 것입니다.

여기에 마무리 단락을 추가하여 일들이 적절한 크기의 텍스트 블록으로 끝나도록 하겠습니다. 왜 일들이 그렇게 끝나기를 원하는지 설명할 수 없지만, 문서 끝에 너무 가까운 제목이 있다면 일들이 이상하거나 균형이 맞지 않게 보일 것이라고 생각하기 때문이라고 가정해야 합니다.

여기서 쓴 것은 아마도 충분히 길지만, 이 마지막 문장을 추가하는 것이 해를 끼치지 않을 것입니다.

## GitHub Flavored Markdown

`remark-gfm`을 사용하여 GitHub Flavored Markdown 지원도 추가했습니다.

`remark-gfm`으로 우리는 마크다운에서 몇 가지 추가 기능을 얻습니다. 예: 자동 링크 리터럴.

www.example.com 또는 https://example.com과 같은 링크는 자동으로 `a` 태그로 변환됩니다.

이것은 이메일 링크에도 작동합니다: contact@example.com.
